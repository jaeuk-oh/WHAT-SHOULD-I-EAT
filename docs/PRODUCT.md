# 냉털메이트 제품 정의

> 누가, 왜 쓰는가. 그래서 무엇을 만들어야 하는가.
> 기술 계획(`LAUNCH_PLAN.md`)의 우선순위는 이 문서에서 나온다.

---

## 1. 문제

한국 1인 가구의 식생활에는 반복되는 손실 구간이 있다.

1. **장은 봤는데 다 못 먹는다.** 대파 한 단, 애호박 한 개를 사면 절반은 버린다.
2. **뭐가 있는지 기억이 안 난다.** 그래서 또 산다. 냉장고 안쪽에서 상한다.
3. **매일 "뭐 먹지"를 정하는 게 피곤하다.** 결정 피로 끝에 배달을 시킨다.
4. **재료는 있는데 뭘 만들 수 있는지 모른다.** 레시피를 검색하면 없는 재료부터 나온다.

이 넷은 하나의 고리다. → **재고를 모르니까 → 또 사고 → 버리고 → 요리를 포기하고 → 배달한다.**
냉털메이트는 이 고리를 **"영수증 한 장"**에서 끊는다. 재고 입력이라는 가장 귀찮은 단계를 없애는 것이 이 제품의 존재 이유다.

## 2. 타겟 사용자

### 1순위: 자취 2~5년차 직장인 (25~34세)

가장 큰 시장이자 가장 아픈 사용자.

- 주 1회 마트/새벽배송으로 장을 본다. 영수증이 매주 생긴다.
- 요리는 하지만 잘하지는 않는다. 30분 넘는 레시피는 안 한다.
- 식비에 민감하다. "이번 달에 얼마 아꼈나"에 반응한다.
- 설거지를 싫어한다. **한 그릇 요리**를 선호한다.

**요구 기능**: 영수증 자동 등록 · 임박 재료 알림 · 15분 이내 1인분 레시피 · 절약 금액 확인

### 2순위: 요리 초보 대학생/사회초년생 (20~26세)

- 예산이 빠듯하고 재료 종류가 적다(계란·양파·대파·냉동만두).
- **실패하지 않는 것**이 최우선. 조리법이 없으면 못 만든다.
- 조리도구가 적다(전자레인지, 프라이팬 하나).

**요구 기능**: 단계별 조리법 · 대체 재료 안내 · "아주 쉬움" 필터 · 적은 재료로 가능한 메뉴

### 3순위: 맞벌이 2인 가구

- 냉장고를 **둘이 공유**한다. 한 사람만 앱을 쓰면 소용이 없다.
- 장보기 중복이 잦다. "우유 있어?"를 카톡으로 묻는다.

**요구 기능**: 가구 공유(같은 냉장고를 두 계정이 봄) · 장보기 리스트 공유 · 2인분 분량

### 사용하지 않을 사람 (의도적으로 버리는 세그먼트)

- 요리를 전혀 안 하고 100% 외식/배달인 사람 → 재고 자체가 없다.
- 대가족·자영업 주방 → 재고 규모가 달라 다른 도구가 필요하다.

## 3. 핵심 사용자 여정과 각 단계의 요구

| 단계 | 사용자가 하는 일 | 여기서 이탈하는 이유 | 필요한 것 |
|---|---|---|---|
| 1. 첫 진입 | 뭐 하는 앱인지 본다 | 가치가 3초 안에 안 보임 | 로그인 전 가치 제안, 로그인 장벽 최소화 |
| 2. 재료 등록 | 영수증을 찍는다 | 인식이 틀림 / 귀찮음 | 정확한 인식 + **쉬운 수정** + 직접 입력 |
| 3. 재고 확인 | 냉장고 앞에서 연다 | 느림 / 재료가 많으면 못 찾음 | 빠른 로딩, 검색, 임박순 정렬 |
| 4. 메뉴 결정 | 추천을 본다 | 만들 수 없는 메뉴가 나옴 | 가진 재료 기반, 대체 재료 안내 |
| 5. 요리 | 만든다 | **조리법이 없음** | 단계별 조리법, 분량 |
| 6. 소진 처리 | 다 먹었다고 표시 | 귀찮음 / 삭제밖에 없음 | 원터치 "다 먹었어요" |
| 7. 재방문 | 다시 연다 | **돌아올 이유가 없음** | 임박 알림, 절약 리포트 |

> 가장 약한 고리는 **5번(조리법 없음)**과 **7번(재방문 이유 없음)**이다.
> 5번은 제품 가치가 완결되지 않는 문제, 7번은 리텐션이 0에 수렴하는 문제다.

## 4. 기능 우선순위

### 반드시 있어야 제품이 성립하는 것 (P0)

| 기능 | 현재 | 근거 |
|---|---|---|
| 영수증 → 재료 자동 등록 | ✅ 있음 | 제품의 존재 이유 |
| 재고 목록 + 임박 D-day | ✅ 있음 | 여정 3단계 |
| 재료 기반 레시피 추천 | ✅ 있음 | 여정 4단계 |
| **단계별 조리법** | ❌ 없음 | 여정 5단계. 없으면 추천이 무용지물 |
| **레시피 영상** | ❌ 없음 | 실제 사용자는 조리법을 주로 유튜브로 본다. AI 텍스트만으로는 신뢰가 부족하다 |
| **"다 먹었어요 / 버렸어요" 구분** | ❌ 삭제만 있음 | 여정 6단계. 낭비 데이터의 원천 |
| **재료 수량** | ❌ 없음 | "우유"만 있고 몇 개인지 모르면 재고가 아니다 |

### 재방문을 만드는 것 (P1)

| 기능 | 근거 |
|---|---|
| **절약 리포트** ("이번 달 12개 살렸어요") | 유일하게 가치를 눈에 보이게 만드는 장치 |
| **임박 재료 강조/요약** | 앱을 열 이유. 푸시 이전의 최소 형태 |
| 재료 검색 | 재고 20개 넘어가면 목록으로는 못 찾는다 |
| PWA 홈 화면 설치 | 냉장고 앞에서 2초 안에 열려야 한다 |

### 규모가 커지면 필요한 것 (P2 — 이번 범위 밖, 설계만)

| 기능 | 왜 나중인가 |
|---|---|
| **푸시 알림(임박 재료)** | 리텐션 최강 레버지만 FCM + VAPID + Vercel Cron + 서비스워커가 필요. 사용자 확보 후 |
| 장보기 리스트 | 부족 재료 자동 수집. 추천 데이터가 쌓인 뒤에 정확해진다 |
| 가구 공유 | 데이터 모델을 `users/{uid}` → `households/{id}`로 바꿔야 함. 되돌리기 어려우니 수요 확인 후 |
| 이메일 영수증 연동 | 리시트호그식 e-receipt. OAuth 범위가 넓어 심사 부담이 크다 |
| 레시피 이미지 생성 | 비용 대비 효과 미검증 |

## 4.5. AI와 영상의 역할 분담

사용자 조사에서 나온 가장 중요한 사실: **사람들은 조리법을 유튜브로 본다.**
AI가 생성한 텍스트 조리법은 "정말 이대로 하면 되나?"라는 의심을 남긴다.
반면 아는 채널의 영상은 그 의심이 없다.

그래서 역할을 나눈다.

> **AI는 "무엇을" 만들지 정한다** — 내 냉장고에 뭐가 있는지는 유튜브가 모른다.
> **영상은 "어떻게" 만드는지 보여준다** — 신뢰는 사람이 만든 콘텐츠에서 나온다.

AI 텍스트 조리법은 없애지 않는다. 영상을 볼 수 없는 상황(조용한 사무실, 데이터 절약)이나
빠르게 재료·분량만 확인할 때 쓰이기 때문이다. 상세 화면에서는 **재료 → 영상 → 텍스트 순서**로 배치한다.

구현은 공식 YouTube Data API + 공식 임베드로 한다. 자막을 긁어 복제하는 방식은
ToS 위반일 뿐 아니라, 비공식 엔드포인트라 언제 깨질지 모른다는 점에서 제품적으로도 나쁜 선택이다.

## 5. 성공 지표

런칭 후 이 숫자들로 판단한다.

| 지표 | 의미 | 목표(런칭 4주) |
|---|---|---|
| 영수증 등록 완료율 | 가입자 중 재료를 실제로 넣은 비율 | 60% |
| 추천 → 조리법 조회율 | 추천이 실제로 쓸모 있었는가 | 40% |
| 주간 재방문율(W1) | 리텐션 | 25% |
| 재료당 소진율(먹음 / 전체) | **제품의 본질적 가치** | 70% |
| 사용자당 월 OpenAI 비용 | 단위경제성 | 300원 이하 |

> 이 중 하나만 본다면 **재료 소진율**이다. 이 숫자가 안 오르면 나머지는 허수다.

## 6. 단위경제성 메모

OpenAI 호출이 유일한 변동비다. 쿼터 설계(`LAUNCH_PLAN.md` 2.2)는 여기서 나왔다.

- 영수증 스캔(Vision)이 가장 비싸다 → 하루 30회로 제한. 정상 사용자는 주 1~2회면 충분하다.
- 추천/조리법은 텍스트라 저렴하다 → 하루 60회.
- 상한을 넘는 사용자는 정상 사용자가 아니라 **비용 공격**으로 본다.
- OpenAI 대시보드의 월 하드리밋을 코드 쿼터의 최후 방어선으로 함께 건다.
