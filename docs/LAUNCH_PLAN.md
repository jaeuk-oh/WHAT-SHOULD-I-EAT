# 냉털메이트 런칭 계획

> 목표: "동작하는 데모"에서 **실제 사용자를 받는 서비스**로 전환한다.
> 작성 시점 기준 코드베이스(약 1,900 LOC, Vite SPA + Vercel Functions + Firebase)를 진단하고,
> 런칭 블로커를 우선순위별로 해결한다.
>
> **누가 왜 쓰는지, 어떤 기능을 요구하는지는 [`PRODUCT.md`](./PRODUCT.md)에 정리했다.**
> 아래 우선순위는 그 제품 정의에서 도출된 것이다.

## 1. 현재 상태 진단

### 잘 되어 있는 것

- 핵심 플로우(로그인 → 영수증 스캔 → 재료 관리 → 추천)가 실제로 동작한다.
- AI API 키가 서버(Vercel Functions)에만 존재하고, 모든 API가 Firebase ID 토큰을 검증한다.
- Firestore 실시간 구독으로 다기기 동기화가 이미 된다.
- 이미지가 클라이언트에서 1280px JPEG로 압축되어 전송된다.
- 트러블슈팅 기록(`docs/TROUBLESHOOTING.md`)이 운영 관점에서 관리되고 있다.

### 런칭 블로커 (이 상태로 사용자를 받으면 사고가 난다)

| # | 문제 | 영향 |
|---|---|---|
| B1 | **API 남용 방어가 전혀 없음** | 계정 하나로 `/api/receipt-scan`을 무한 호출 가능. OpenAI Vision 호출이라 **비용 폭탄**이 즉시 발생. 서비스 존속 위협 1순위 |

| B6 | **실존 인물 실명 시드 데이터** | 실제 인물을 저작자로 표기한 가짜 레시피 → 퍼블리시티권/명예 문제 |
| B7 | **오류 UX가 `alert()`** | 브라우저 기본 얼럿, 모바일에서 조악. 실패 원인 안내 부족 |
| B8 | **인앱 브라우저 로그인 실패** | `signInWithPopup`만 사용. 카카오톡·인스타그램 인앱 브라우저에서 팝업 차단 → 한국 사용자 유입 경로에서 로그인 자체가 안 됨 |
| B9 | **보안 헤더·PWA·SEO 미설정** | CSP 등 헤더 없음, 홈 화면 설치 불가, 공유 시 미리보기 없음 |
| B10 | **CI 없음** | 타입 에러가 있는 채로 배포될 수 있음. 실제로 과거에 ESM 임포트 문제로 전체 API가 500이 난 이력 있음 |

## 2. 아키텍처 설계

### 2.1 현재 → 목표

```
[현재]
브라우저 SPA ─┬─ Firebase Auth / Firestore (직접, 규칙만으로 보호)
              └─ /api/{receipt-scan,recommend}  ── 토큰 검증 → NVIDIA NIM

[목표]
브라우저 SPA ─┬─ Firebase Auth / Firestore (직접, 규칙 강화)
              └─ /api/*  ── 토큰 검증 → [쿼터·레이트리밋 게이트] → NVIDIA NIM
                              │
                              └─ Firestore(Admin SDK): 사용량 카운터 / 계정 삭제
```

핵심 원칙: **읽기·쓰기 중 "돈이 나가거나 신뢰가 필요한 것"만 서버로 보낸다.**
재료·저장 레시피 같은 사용자 소유 데이터는 지금처럼 클라이언트 직결 + 보안 규칙으로 두는 것이
비용·지연 모두 유리하다. 서버는 (a) NVIDIA NIM 프록시, (b) 사용량 집계, (c) 계정 삭제만 담당한다.

### 2.2 남용 방어 설계 (B1)

2단계 게이트를 `/api/*` 앞에 둔다.

- **단기 레이트리밋**: 사용자당 슬라이딩 윈도우. 연타·자동화 스크립트 차단.
- **일일 쿼터**: 사용자당 하루 호출 상한. 비용 상한선 역할.

카운터는 Firestore `usage/{uid}` 문서에 **Admin SDK 트랜잭션**으로 기록한다.
클라이언트는 이 문서를 읽을 수만 있고(잔여 횟수 표시용) 쓸 수 없다.

> 왜 Redis가 아니라 Firestore인가: 이미 Firestore를 쓰고 있어 인프라가 늘지 않는다.
> 이 서비스의 호출 빈도(사용자당 하루 수~수십 회)에서는 Firestore 트랜잭션으로 충분하다.
> 트래픽이 커지면 이 레이어만 Upstash Redis로 교체하면 된다(인터페이스는 `api/_quota.ts` 하나).

**서비스 계정이 설정되지 않은 경우**: 인스턴스 메모리 기반 폴백으로 동작하되 경고 로그를 남긴다.
(서버리스라 인스턴스마다 독립 → 방어력이 약하므로 프로덕션에서는 반드시 서비스 계정을 설정한다.)

### 2.3 보안 규칙 설계 (B2)

- `users/{uid}/**` — 본인만 읽기/쓰기 (유지)
- `usage/{uid}` — 본인 읽기만, 쓰기는 서버(Admin)만
- `recipes/{id}` — 누구나 읽기, **클라이언트 생성/삭제 금지**.
  좋아요만 예외적으로 허용하되 다음을 규칙에서 강제:
  - `likes` 필드 외 다른 필드 변경 불가
  - 정확히 +1만 가능
  - 이미 `users/{uid}/likes/{recipeId}`가 있으면 불가 (중복 방지)
- `users/{uid}/likes/{recipeId}` — 본인만. 생성만 가능(취소 시 삭제 허용).

### 2.4 데이터 모델 (추가/변경분)

| 경로 | 용도 | 접근 |
|---|---|---|
| `usage/{uid}` | `{ day, dayCount, window[] }` 사용량 카운터 | 클라 읽기 / 서버 쓰기 |
| `users/{uid}/likes/{recipeId}` | 좋아요 중복 방지 | 본인 |
| `users/{uid}/ingredients/*` | 재료 (기존) | 본인 |
| `users/{uid}/saved/*` | 저장 레시피 (기존) | 본인 |
| `recipes/*` | 공유 레시피 (기존) | 공개 읽기 |

### 2.5 API 표면

| 엔드포인트 | 메서드 | 비용 | 쿼터 |
|---|---|---|---|
| `/api/receipt-scan` | POST | Vision (비쌈) | 하루 30회 |
| `/api/recommend` | POST | 텍스트 | 하루 60회 |
| `/api/recipe-detail` | POST | 텍스트 | 하루 60회 |
| `/api/account-delete` | POST | — | 하루 5회 |

모든 응답은 `{ error }` 또는 도메인 페이로드. 쿼터 초과 시 **429 + 재시도 시각**을 반환한다.

## 3. 실행 계획 (우선순위)

기술 블로커(B1~B10)와 제품 요구(`PRODUCT.md` 4장)를 하나의 목록으로 합쳤다.

### P0 — 런칭 전 반드시

**(가) 서비스 존속·법적 요건**

1. **레이트리밋 + 일일 쿼터** (B1) — `api/_quota.ts`, 전 엔드포인트 적용, 429 UX
2. **Firestore 규칙 강화 + 좋아요 어뷰징 방지** (B2)
3. **약관·개인정보처리방침·회원 탈퇴** (B3)
4. **URL 라우팅** (B4) — 모바일 뒤로가기 정상화

**(나) 제품이 성립하기 위한 기능** — 여기가 빠지면 "쓸 수는 있지만 쓸모는 없는" 앱이 된다

5. **단계별 조리법** (B5) — 여정 5단계. 추천만 있고 만들 수가 없었다
6. **"다 먹었어요 / 버렸어요" 구분** — 여정 6단계. 지금은 삭제뿐이라 낭비 데이터가 남지 않는다
7. **재료 수량** — 수량 없는 재고는 재고가 아니다

### P1 — 재방문을 만드는 것

8. **절약 리포트** — 가치를 눈에 보이게 하는 유일한 장치. 재방문 동기
9. **임박 재료 요약 강조** — 앱을 열 이유(푸시 이전의 최소 형태)
10. **재료 검색** — 재고 20개를 넘으면 목록으로는 못 찾는다
11. **토스트·에러바운더리·인앱 브라우저 로그인 폴백** (B7, B8)
12. **PWA·SEO·보안 헤더** (B9) — 냉장고 앞에서 2초 안에 열려야 한다
13. **실명 시드 데이터 교체** (B6)

### P2 — 운영 체력

14. **CI(타입체크·빌드)** (B10), 운영 런북, README 갱신

### 이번 작업 범위 밖 (설계만, `PRODUCT.md` 4장 P2 참고)

- **푸시 알림(임박 재료)** — 리텐션 최강 레버. FCM + VAPID + Vercel Cron + 서비스워커 필요.
  구조는 이미 준비됨: `users/{uid}/fcmTokens` 추가 → Vercel Cron이 매일 아침 D-1 재료를 조회해 발송.
- 장보기 리스트 / 가구 공유 / 이메일 영수증 연동 / 레시피 이미지 생성

## 4. 런칭 체크리스트

배포 전:

- [ ] `npm run lint` (타입체크) 통과
- [ ] `npm run build` 통과
- [ ] Vercel 환경변수 등록: `NVIDIA_API_KEY`, `FIREBASE_SERVICE_ACCOUNT`, `VITE_FIREBASE_*`
- [ ] Firebase 콘솔 → Authentication → 승인된 도메인에 배포 도메인 추가
- [ ] Firebase 콘솔 → Firestore 규칙에 `firestore.rules` 반영
- [ ] 약관/개인정보처리방침의 **운영자 정보 플레이스홀더 채우기** 및 법률 검토
- [ ] NVIDIA 계정 대시보드에서 **크레딧·사용량 한도** 확인 — 코드 쿼터의 최후 방어선

배포 후 스모크 테스트:

- [ ] `/` 200, 로그인 동작 (데스크톱 + 모바일 + 카카오톡 인앱 브라우저)
- [ ] 미인증 `POST /api/recommend` → 401
- [ ] `GET /api/recommend` → 405
- [ ] 영수증 스캔 → 재료 등록 → 추천 → 상세 → 저장 전체 플로우
- [ ] 쿼터 초과 시 429와 안내 문구 노출
- [ ] 뒤로가기로 홈 복귀, 새로고침 시 현재 화면 유지
- [ ] 회원 탈퇴 → 재로그인 시 데이터가 비어 있음
